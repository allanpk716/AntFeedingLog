# 备份从"单库文件"升级为"数据包"（库 + 巢况照片）

巢况照片需求（2026-09-19，与网页端同批）落地时必须在存储上表态：照片以 BLOB 入库则备份机制一行不改，但库体积从 MB 级涨到 GB 级，保留 30 份的自动备份会吃穿磁盘；照片存库外又不进备份，则恢复/换机即丢照片，与"恢复=整体替换全部数据"的语义矛盾。决定：照片存数据目录 `photos/` 文件夹（库内只存元数据：路径、日期、备注），**备份产物从单个 .db 升级为"数据包"**（库+照片打包成单文件）；恢复同时认两种来源——旧裸库（不含照片，库走既有 staging 迁移链升级后替换）与新数据包（解包校验、照片放回）；pre-restore 快照同步升级为数据包，"恢复可反悔"对照片同样成立。恢复旧裸库时 `photos/` 保留不动（恢复这个动作绝不顺手删文件，库回滚后照片暂成无害孤儿），恢复数据包时 `photos/` 被包内内容整体替换（整包替换语义）。

## Consequences

- "备份"的领域含义从"拷库文件"变为"拷数据包"，CONTEXT.md 已同步改写。
- 每份备份体积变大（照片压缩后单张约数百 KB）；靠保留份数设置控磁盘。
- 旧版本应用恢复不了数据包（其文件选择只认 .db）——数据包只能被 ≥ 本版本的应用恢复，视为可接受；裸库永远可恢复。
- 导出（CSV/JSON）同步补巢况数据，与备份是两条路，互不影响。
