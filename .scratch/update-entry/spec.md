# 升级入口前置：主页面按钮 + 托盘检查 + 红点角标

Status: ready-for-agent

## Problem Statement

升级功能藏在设置弹窗的「更新」页签深处：想知道有没有新版本，得点 ⚙设置 → 翻到「更新」页签 → 点「立即检查更新」，三步且入口难记。应用收到托盘后想查更新更是无路可走——托盘右键菜单只有版本灰显项、显示主窗口、退出。界面对「有新版可装」也没有任何感知，唯一的提示是每天一条系统通知，文案还指的还是那条绕远的设置页老路。

## Solution

三条新触达路径，共用现有升级流水线（设置「更新」页签的完整安装流原样复用，零重复建设）：

1. **主页面按钮**：顶栏「⚙设置」旁加一个同款图标按钮，点一下 = 设置弹窗直接开在「更新」页签并自动开始检查，一步到位。
2. **托盘右键「检查更新…」**：后台静默查，智能分流——有新版自动弹出主窗口直达更新页签接着装；无新版只发一条「已是最新」通知；失败发带原因的失败通知。
3. **红点角标**：主页面按钮在有新版可装时亮红点。红点表达一个事实——「远端有比当前新的版本」，数据落库持久化（重启不丢、离线启动也在），只随事实变：任一检查结果「已是最新」即灭、装完重启版本追上自然灭，「暂不更新」不灭。

每日自动检查的系统通知文案同步改为指向新入口。

## User Stories

1. 作为桌面端饲养人，我想在主页面顶栏一眼看到「检查更新」按钮，这样不必记得升级功能藏在设置弹窗的哪个页签里。
2. 作为桌面端饲养人，我想点一下主页面「检查更新」按钮就打开设置弹窗的「更新」页签并自动开始检查，这样一步完成原来三步的操作。
3. 作为桌面端饲养人，我想在托盘图标右键菜单里看到「检查更新…」项，这样应用收到托盘/后台时也能直接触发检查。
4. 作为桌面端饲养人，我想托盘检查发现新版本时自动弹出主窗口并直达更新页签自动检查，这样从「发现新版」到「开始安装」不需要任何多余操作。
5. 作为桌面端饲养人，我想托盘检查结果是「已是最新」时只收到一条系统通知而不弹窗口，这样确认无更新不打扰当前工作。
6. 作为桌面端饲养人，我想托盘检查失败（网络断/超时）时收到一条带原因的失败通知，这样我知道点了没白点、失败有原因可循。
7. 作为桌面端饲养人，我想主页面「检查更新」按钮在有新版可装时亮红点，这样不主动检查也知道有新版本等着装。
8. 作为桌面端饲养人，我想红点在重启应用后依然亮着（只要远端确实还有比当前新的版本），这样不会因为重启而错过升级提示。
9. 作为桌面端饲养人，我想离线启动时红点状态依然正确（读的是上次检查落库的结果），这样断网不吞掉提示。
10. 作为桌面端饲养人，我想任一检查路径（每日自动 / 主页面 / 托盘）发现新版本后红点都亮，这样提示口径一致、不因入口不同而不同。
11. 作为桌面端饲养人，我想任一检查结果为「已是最新」时红点熄灭，这样红点永远只表达真实事实。
12. 作为桌面端饲养人，我想安装完成重启后红点自然熄灭（当前版本已追上落库版本），这样不需要手动清除。
13. 作为桌面端饲养人，我想点「暂不更新」后红点保持亮着，这样被动提醒不被临时决定抹掉。
14. 作为桌面端饲养人，我想每日自动检查的系统通知文案指向新的主页面入口，这样按通知指引能最快走到安装。
15. 作为桌面端饲养人，我想从主页面按钮或托盘直达更新页签时自动开始检查，这样不用到了地方再点一次「立即检查更新」。
16. 作为桌面端饲养人，我想平时从设置弹窗自己翻到「更新」页签时不自动发起网络检查，这样浏览设置不产生多余网络请求。
17. 作为桌面端饲养人，我想升级安装的完整流程（下载进度、失败重试、手动下载出口、升级前自动备份）在新入口触达后保持原样，这样熟悉的兜底路径都还在。
18. 作为桌面端饲养人，我想安装已在进行中时重复触达不误报失败也不重复安装，这样手快连点没有副作用。
19. 作为桌面端饲养人，我想检查进行中界面给出「检查中」反馈且不可重复触发，这样不会并发跑两轮检查。
20. 作为桌面端饲养人，我想托盘检查期间没有窗口闪烁（纯后台静默），只有结果才反馈，这样检查过程本身不打扰。
21. 作为桌面端饲养人，我想主页面按钮与 ⚙设置同款视觉风格并带悬停提示，这样顶栏风格统一、功能可预期。
22. 作为网页端用户，我在网页端看不到任何升级入口，这样界面不出现我无权使用的功能（更新是桌面端专属，词汇表边界不变）。

## Implementation Decisions

- **主页面按钮**：顶栏 tools 区（「＋新建窝」「⚙设置」同排）新增 ghost 图标按钮（上升箭头类图标，悬停提示「检查更新」），桌面端专属（isTauri 守卫，同 ⚙设置）。
- **直达机制**：SettingsDialog 新增 initialTab 入参（默认值维持现状不变）；UpdatePanel 新增 autoCheck 入参（挂载即触发一次检查）。主页面按钮点击 = 打开设置弹窗、落在「更新」页签、autoCheck。
- **托盘菜单**：托盘右键菜单在版本灰显项之下新增「检查更新…」项；点击在后台线程走手动检查路径（不写每日记账，与每日检查互不干扰）。
- **托盘分流决策**（纯函数）：检查结果 → 有新版：显示主窗口并广播「直达更新页签」事件 / 无新版：发「已是最新 vX」系统通知 / 失败：发「检查更新失败：原因」通知。开窗、聚焦、通知发送、事件发射是 Tauri 胶水。
- **直达事件**：Rust → 前端事件，App.vue 订阅后打开设置弹窗于「更新」页签；设置弹窗已开则切换页签；安装进行中不重复触发检查（复用 UpdatePanel 现有安装态守卫）。
- **红点持久化**：settings 键值表存「已发现的可升级版本号」（空/缺 = 无）。写时机：任一检查路径结果为有新版；清时机：任一检查路径结果为已是最新。
- **红点判活**：数值语义版本比较（点分段按数值比，避免 `"0.10.0" < "0.9.0"` 字符串序坑），落库版本严格大于当前版本才亮；比较在 Rust 侧完成。
- **红点刷新**：App.vue 挂载读一次；订阅 Rust 在每次检查落库后广播的「可用版本变化」事件即时刷新。
- **每日通知文案**：notify 文案函数改为指向主页面新入口（如「点主窗口右上『检查更新』按钮即可安装」）。
- **并发与防重入**：检查是只读网络操作，托盘与界面并发检查无害；安装防重入沿用现有守卫。
- **边界**：网页端 IPC 白名单不放行任何新增命令；红点与直达事件均为桌面端。不立 ADR（可逆、不意外、无真权衡）；不改 CONTEXT.md 词汇表（无新领域概念）。

## Testing Decisions

- 好测试只测外部行为：纯函数喂输入断言输出；组件测试断言渲染结果与用户可感知的交互，不断言内部状态。
- **Rust 纯逻辑**（updater.rs 测试模块，mem_conn + FakeChecker 先例）：红点状态机（发现写键 / 已是最新清键 / 读键判活）、版本比较边界（0.10.0 > 0.9.0、等版本不亮、段数不等的版本号）、托盘分流决策三态、通知文案函数。
- **前端纯逻辑**（updaterUi.ts + 同名测试先例）：红点展示映射等新增小函数。
- **组件测试**（Vitest + happy-dom，均为既有同名测试先例）：App 层——按钮桌面端渲染、网页端不渲染、点击打开设置弹窗并传「更新」页签、红点随事件亮灭；SettingsDialog——initialTab 落位、默认仍是首页签；UpdatePanel——autoCheck 挂载即查一次、普通挂载不自动查。
- **不进单测**：托盘菜单构建与点击、开窗/聚焦、系统通知发送、事件发射（项目惯例：Tauri 侧系统行为不进单测）。
- 全量验证：vitest + vue-tsc + cargo test。

## Out of Scope

- 托盘图标本身的角标（overlay icon）。
- 网页端任何更新能力。
- 启动时静默轻查（红点数据源已定为落库，无需启动网络请求）。
- 系统通知可点击跳转（通知只指路，不可点直达）。
- 自动下载 / 自动安装（仍需用户确认「下载并安装」）。
- 「更新」页签 UI 重构（UpdatePanel 原样复用）。

## Further Notes

- 与 CONTEXT.md「桌面端 / 网页端」边界一致：更新属桌面端系统管理能力，词汇表表述原样成立。
- 红点语义：「远端有比当前新的版本」这一事实，只随检查结果与版本追上变化，不随用户态度（暂不更新）变化。
- 检查总超时 30 秒（CHECK_TIMEOUT）沿用，托盘检查同受此约束。
- 本 spec 由 grilling 两轮 + to-spec 接缝确认产生（2026-09-29）。
